# VibeCheck 前端高保真升级设计

**日期：** 2026-08-29  
**状态：** 已确认  
**参考方向：** [When You Wish Upon a Starboy](https://onepagelove.com/when-you-wish-upon-a-starboy)

## 1. 目标

在不重写现有路由、业务状态、API 客户端和提交幂等逻辑的前提下，把现有功能型低保真前端升级为可正式交付的高保真产品界面。

公开前台与任务页面全面升级；后台保持紧凑、工具化。参考站只提供构图、滚动节奏和视觉强度，不复制其硬件造型、角色、品牌字形或素材。

本阶段保留当前两类作品模型、18 个前台路由、后台路由、发布黄金路径及其测试。视觉升级不能把本地模拟冒充真实部署验收，也不能扩展审核决定、首次发布和 ProjectUpdate 回流的业务范围。

## 2. 设计原则

1. **作品是主角。** 巨幅媒体优先展示真实作品截图，而不是无关装饰图。
2. **强视觉不牺牲任务效率。** 表单位置、错误信息和主要操作保持稳定。
3. **借鉴方法，不复制外观。** 使用超大标题、越界裁切、长滚动和少量高饱和色，但建立原创 VibeCheck 视觉对象。
4. **业务状态是唯一事实源。** 视觉组件只消费现有状态，不复制提交、上传、审核或比较逻辑。
5. **渐进增强。** 无脚本动画、加载失败和减少动效模式下，内容与操作仍完整可用。
6. **分轮可交付。** 每轮形成可独立测试、截图复核、提交、推送并通过 CI 的成果。

## 3. 视觉语言

### 3.1 构图

- 页面采用白色或微暖白舞台，近黑色文字形成主要对比。
- Hero 使用超大、紧凑、可换行标题；桌面标题可占 45%–65% 视口高度，移动端不遮挡主要操作。
- 作品媒体允许越过常规内容容器并进行裁切、重叠和轻微倾斜，但正文保持稳定阅读列宽。
- 长页面通过大图、短文案、状态图形、作品带和密集信息区交替形成节奏。
- 不使用重复的等宽三列卡片填满所有区块；根据内容采用单幅舞台、横向作品带、非对称网格和紧凑列表。

### 3.2 色彩

- 主舞台：`#F7F7F2`。
- 主文字：`#111111`。
- 反相表面：`#111111`，文字使用 `#F7F7F2`。
- 核心强调：荧光绿 `#B8FF3D`。
- 分类强调：亮黄 `#FFD93D`、紫色 `#B78CFF`、青色 `#61E7F2`。
- 错误、警告和成功继续使用可访问的语义色；状态不能只依赖颜色。
- 高饱和色每个视口最多同时出现两种主强调，避免彩色噪声。

### 3.3 字体

- 中文展示标题使用本地系统宽重字体栈：`Arial Black`, `PingFang SC`, `Microsoft YaHei`, sans-serif。
- 正文和控件使用：`Inter`, `PingFang SC`, `Microsoft YaHei`, system-ui, sans-serif；若仓库没有 Inter 字体资源，则使用系统回退，不发起第三方字体请求。
- 英文品牌字形可以在后续实现中内置一个不超过 80 KB WOFF2 的 OFL 字体，但不得引入全量中文 Web Font。

### 3.4 原创品牌对象

- 核心对象为“观察镜片＋确认标记”的抽象 `Vibe Lens`，使用 SVG/CSS 实现。
- Lens 可通过瞳孔方向、环形状态和强调色表达作品类别、匹配、加载、可访问性和审核状态。
- Lens 不采用五角星外形、金属宠物外壳或与 Starboy 相似的眼睛组合。
- 没有作品截图时，用作品 ID、分类和状态确定性生成占位构图；同一作品跨页面保持一致。

## 4. 页面模板

### 4.1 Editorial Landing

覆盖 P01 作品广场、P02 分类总览、P04 最新动态和 P18 关于。

模板由 `EditorialHero`、章节导语、巨幅作品舞台、横向作品带、非对称内容区和完整页脚组成。P01 作为全站视觉样板，先建立品牌尺度、导航、卡片、媒体和滚动节奏。

### 4.2 Discovery Canvas

覆盖 P03 分类详情、P05 搜索、P06 想法分析和 P07 匹配结果。

入口区保持强视觉；进入筛选和结果后切换为稳定网格。筛选、匹配原因、证据与未知状态保持原有语义和键盘操作。移动端筛选使用抽屉或折叠区域，不能挤压结果卡片。

### 4.3 Project Story

覆盖 P08 作品详情和 P14 作者主页。

首屏围绕真实作品截图、名称、定义、作者和访问状态；后续使用事实档案、流程、开发信息、时间线、资产、关系和讨论形成编辑式长页。事实未知、证据不足和疑似迁移状态仍必须明确可见。

### 4.4 Decision Workspace

覆盖 P09 比较、P15 个人中心和 P16 通知。

使用更高信息密度，不强行套用营销页结构。桌面比较保留并列关系；390 与 768 采用纵向作品卡或可访问的横向区域。决策记录、收藏、草稿和通知状态由现有数据驱动。

### 4.5 Immersive Task Flow

覆盖 P17 登录、P10 发布入口、P11 发布编辑与预览提交、P12 作者验证、P13 作品更新。

统一由 `TaskShell` 提供任务标题、步骤轨道、主要输入区、上下文预览和状态反馈。任务页面同样进行完整品牌升级，但动画不能移动已聚焦输入、隐藏错误、改变按钮位置或阻断提交。

P10/P11 保持现有主流程：URL 检查与建草稿、四步本地填写、canonical PATCH、封面上传与引用、证据、preview/submit、`pending_review`。高保真层不得改变请求顺序、版本、operation ID、submission key 或冲突处理规则。

### 4.6 Admin Utility

后台仅同步字体、基础色、按钮、输入、表格、状态和焦点规范。保留紧凑导航、高密度表格、筛选和批量操作，不使用巨幅 Hero、视差或营销式长滚动。

## 5. 组件边界

### 5.1 新增展示组件

- `BrandMark`：静态品牌标记。
- `VibeLens`：确定性生成类别和状态视觉；只接收展示属性。
- `EditorialHero`：标题、说明、操作和媒体槽位。
- `ProjectMediaStage`：真实截图、响应式资源、加载失败及占位图。
- `SectionLead`：章节标题、说明和可选操作。
- `MarqueeStrip`：可键盘访问的作品或状态横向带；不自动抢占焦点。
- `Reveal`：基于 IntersectionObserver 的一次性进入效果；减少动效模式立即呈现。

### 5.2 新增任务组件

- `TaskShell`：任务页面结构，不读取或修改业务状态。
- `StepRail`：显示当前、完成和不可达步骤。
- `LivePreview`：把传入草稿映射为预览，不保存草稿副本。
- `StatusBeacon`：统一显示检查、上传、保存、提交与审核状态，同时提供文本标签。
- `ErrorSummary`：聚合字段错误并允许键盘跳转到对应输入。

### 5.3 现有组件

`Button`、`Input`、`Card`、`Tag`、`Tabs`、`Drawer`、`Modal`、`Feedback` 与页面路由接口保持兼容，先通过内部样式和可选展示属性升级。禁止为了视觉效果让页面复制组件内部 CSS 或业务判断。

## 6. 动效

- 第一阶段只使用 CSS、Web Animations API 和一个小型 `useReveal` hook，不引入 GSAP 或 Framer Motion。
- 动画仅修改 `transform` 与 `opacity`；不对输入、表格或错误信息做持续位移动画。
- Hero 媒体可做最大 24px 的滚动位移；作品卡进入位移不超过 32px，持续时间 180–500ms。
- 横向内容带由用户滚动或按键控制，不自动无限滚动。
- `prefers-reduced-motion: reduce` 下关闭视差、漂浮、错位进入和平滑滚动。
- 路由切换不做阻断式全屏转场。

## 7. 素材策略

- 真实作品截图优先，提供 `avif`、`webp` 与回退格式；资源在构建前完成压缩。
- 单张桌面图片不超过 350 KB，移动端不超过 180 KB；首屏媒体总传输预算不超过 900 KB。
- 非首屏图片使用原生懒加载并声明宽高，避免布局跳动。
- 生成或绘制的品牌素材必须原创并进入仓库受版本控制；不得依赖运行时第三方图库。
- 现有 wireframe/placeholder 数据继续可用，但由 `ProjectMediaStage` 统一呈现。

## 8. 状态与错误处理

- URL 检查、上传、保存和提交状态固定在对应操作区域，预留尺寸以避免页面跳动。
- 字段错误紧邻输入；存在多个错误时，同时显示 `ErrorSummary`。
- 网络失败保留输入、幂等键和重试能力；视觉层不得创建新的请求重放机制。
- 图片失败显示同作品一致的 `VibeLens` 占位图和替代文本。
- `pending_review` 使用完整结果场景，明确提交内容、后续状态和可返回路径。
- 401/403、409、410、422 和传输错误沿用现有业务分流，仅统一视觉表达。

## 9. 性能与可访问性

- 新增视觉运行时代码不超过 15 KB gzip。
- 通过路由级 `lazy`/`Suspense` 拆分前台、任务和后台页面；升级后初始入口包不得高于改造前基线。
- 所有交互支持键盘；焦点顺序与视觉顺序一致。
- 文本与背景对比满足 WCAG 2.2 AA；焦点指示器不依赖阴影在复杂图片上可见。
- 语义状态同时包含图形、文字和可读标签。
- 390、768、1440 三个视口不得出现非预期横向溢出、粘性导航遮挡或不可触达操作。

## 10. 测试与验收

- 保持现有全量 Vitest 和契约门禁通过；当前已知基线为 63 个测试文件、348 项测试。
- P10/P11 发布黄金路径继续验证请求、版本和 `pending_review`，不能替换为纯视觉断言。
- 为新组件覆盖：确定性占位、媒体失败、减少动效、步骤状态、错误摘要和键盘操作。
- Playwright 在 390、768、1440 视口覆盖核心前台与完整发布主流程。
- 每轮输出代表页面截图，检查视觉层级、裁切、文字换行、焦点和错误状态。
- 构建记录 JS、CSS 与首屏媒体大小；超过预算则该轮不能完成。
- 每轮先运行聚焦测试，再运行 lint、typecheck、build、全量测试和相关 E2E；Sol 最终复核后自动提交、推送并确认远端 CI。

## 11. 实施切片

1. **视觉基础与 P01 样板：** 令牌、基础组件、品牌对象、动效设施、导航、页脚和作品广场三档响应式。
2. **P10/P11 发布主流程：** URL 检查、四步编辑、材料、预览、提交与 `pending_review` 的完整高保真升级。
3. **发现链路：** P02–P07 的分类、搜索、想法分析和匹配结果。
4. **作品叙事与比较：** P08、P09、P14。
5. **账户与后续任务：** P12、P13、P15、P16、P17、P18。
6. **后台与全站门禁：** 后台基础统一、路由懒加载、全路由视觉与功能验收。

每个切片只在上一切片功能、视觉、响应式和 CI 门禁通过后开始；每轮形成独立提交并自动推送当前分支。

## 12. 非目标

- 不复制 Starboy 的品牌、角色、硬件造型、字形或素材。
- 不在本阶段改变服务端契约、审核规则或数据库模型。
- 不把审核决定、首次发布和 ProjectUpdate 回流纳入当前发布主流程验收。
- 不引入大型动画框架、3D/WebGL 场景或运行时图片生成。
- 不因视觉升级删除未知、证据、冲突、权限、失败或减少动效状态。
