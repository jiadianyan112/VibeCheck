# 首期品类切换影响说明

> 项目：VibeCheck  
> 变更类型：首期种子品类切换  
> 文档版本：v1.0  
> 日期：2026 年 8 月  
> 用途：项目内部决策、原型同步与开发 PRD 更新依据

## 一、切换结论

VibeCheck 首期种子品类从“公开可访问的 AI 学习与题库 Web 工具”切换为“公开可访问、由 AI 编程工具辅助开发的个人主页与作品集 Web 网站”。

该变更只替换 MVP 阶段用于验证完整循环的数据切口，不重做 VibeCheck 的长期产品方向。产品仍然是面向 Vibe Coding 创作者的作品发现、发布与生命周期资产平台；社区前台、结构化作品档案、生命周期事实、证据和复用关系继续保留。

## 二、为什么切换

### 1. 原供给假设失效

原首期方案依赖在单一类别中建立 30—50 个公开可访问、结构相似、信息可核验且适合比较的高质量作品。实际供给检查显示，该类别公开作品数量、访问稳定性和结构一致性不足，难以在合理冷启动成本内形成稳定集合。

供给不足不仅影响首页丰富度，也会连锁削弱分类密度、查同类结果、比较页差异、复用资产和生命周期事件。即使原型流程可运行，真实数据仍可能长期停留在“少量示例＋宽泛相邻结果”的状态。

### 2. 新品类更适合社区前台

个人主页与作品集具有公开访问率高、截图价值强、视觉差异明显和自然浏览需求强等特点。用户在开始开发前会主动查看同类案例，收藏喜欢的结构和风格，并寻找模板、源码、组件与部署方式。

该品类同时具备丰富的开源仓库、Starter、模板、页面布局、组件、动画和设计稿，更适合验证“作品发现—收藏/比较/复用—开发—发布回流”的完整循环。

### 3. 新品类更适合建立作品关系

个人网站常见 Inspired by、参考、Fork、Remix、基于模板和使用组件等清晰关系。平台可以逐步回答“这个作品参考了谁”“一个模板衍生了多少网站”“哪些结构被大量采用”，更早验证作品关系网络的长期价值。

## 三、原假设如何调整

| 原假设 | 失效或变化 | 新假设 |
| --- | --- | --- |
| 开发前核心问题是判断需求是否值得继续 | 对个人网站而言，“是否开发”通常不是主要障碍 | 用户更需要确定类型、结构、视觉、实现和复用起点 |
| 高价值行动集中在继续、调整、复用、暂停 | “暂停”在个人网站中的权重明显降低 | 主要行动改为收藏参考、开始开发、调整方向和复用资产 |
| 目标用户、输入输出和功能流程可识别同类 | 这些字段无法解释个人网站差异 | 使用作者身份、网站类型、用途、结构、项目展示、视觉和实现 |
| 30—50 个作品可以形成种子库 | 新品类供给更充足且视觉差异更大 | 建立 64 个作品、8 个策展子群的高质量种子库 |
| 关系声明可延后至 P1 | 新品类的模板与派生关系直接影响复用价值 | 关系展示进入 P0，声明与审核进入 P0.5 |
| 灵感浏览者不是首期重点 | 强视觉品类存在自然、重复的浏览需求 | 灵感浏览者进入核心用户状态和社区指标 |

## 四、保持不变的产品能力

以下能力不因切换而取消或降级：

- 社区前台＋结构化作品档案内核；
- 作品广场、分类/专题、最新动态、全局搜索、查同类、详情、比较、发布、作者主页、个人中心和后台；
- 浏览、收藏、点赞、评论、关注更新、分享、加入比较、发布和更新；
- 唯一 `project_id`、跨来源作品身份和历史地址；
- 平台建档、作者主动发布、用户线索和重复合并；
- 已有档案的低频作者身份验证与权限关联；
- 访问状态、最后验证时间、证据类型、争议和历史留痕；
- 生命周期事件、状态监测、异常复核和恢复；
- 可复用资产、作品关系和比较会话；
- 后台建档、发布审核、身份审核、证据、状态、关系和社区治理；
- 不根据作品数量、访问状态或互动量推断商业成功。

## 五、发生调整的模块

### 1. 产品价值表达

从“开发前判断是否继续”调整为“获得灵感、收藏参考、确定结构、选择视觉与技术方向、复用起点、开始开发和发布回流”。通用暂停动作保留，但降为次级。

### 2. 分类与数据字段

删除原首期品类的目标用户、输入、输出、练习形式、反馈和记录等专属字段。通用 `ProjectCore` 与 `PortfolioSchemaV1` 正式分层，避免首期字段继续污染作品主对象。

### 3. 首页与卡片

首页频道改为编辑精选、最新/更新、开源可 Fork、网站类型、视觉方向、优秀 Case Study、可复用起点等；卡片以真实截图为第一信息层，结构化标签负责解释和筛选。

### 4. 搜索与查同类

意图解析改为作者身份、网站类型、用途、页面结构、内容模块、项目展示、视觉/布局/主题、交互、技术实现和复用条件；原“目标用户”不再作为高权重字段。

### 5. 作品详情与比较

详情档案改为定位、结构、项目展示、视觉交互、站点能力、实现、资产、生命周期和关系。比较维度彻底替换，并增加“参考亮点”和更清晰的资产许可/可用性表达。

### 6. 发布与更新

发布表单收集 `PortfolioSchemaV1` P0 字段；P0.5 增加可跳过的参考与复用来源。更新事件更重视新增项目、Case Study、博客、简历、视觉改版、主题、技术栈和开放源码。

### 7. 指标与冷启动

北极星指标改为每周有效发现后产生创作推进动作的创作者数。冷启动统一为 64 个作品、8 个策展子群，每群至少 6 个，至少 24 个开源/可 Fork、至少 32 个含复用资产。

## 六、数据模型影响

### 1. 目标模型

`ProjectCore` 保存身份、作者、URL、媒体、开发工具、技术栈、部署、状态、生命周期、资产、关系、证据和审核等跨品类数据，并通过 `category_id`、`category_schema_version`、`category_data` 挂载 `PortfolioSchemaV1`。

`PortfolioSchemaV1` P0 保存网站类型、作者身份、建站目的、页面结构、内容模块、项目展示、视觉、布局、色彩、主题、交互、响应式和博客能力；P1 保存 CMS、多语言、联系方式、简历下载和 AI 功能。

### 2. 当前原型数据迁移

当前原型没有生产数据库，因此本轮不需要在线数据迁移或兼容发布。后续同步原型时应：

1. 保留所有通用类型、状态、证据、事件、资产、关系和权限行为；
2. 从 `Project` 主对象移除首期旧 Category 字段，迁移为 `categoryData`；
3. 新建 `PortfolioSchemaV1` 类型、枚举、校验和模拟数据；
4. 重建搜索映射、分类目录、比较矩阵、发布字段和测试夹具；
5. 保留旧模拟数据仅作为独立测试夹具或删除前确认无用户依赖，不与新品类正式数据混用。

## 七、原型影响矩阵

修改级别定义：

- **无需修改**：页面结构和主要内容均可直接保留；
- **数据/内容层修改**：路由、页面模块和主要操作不变，只替换字段、标签、频道、文案、数据和测试任务；
- **局部结构修改**：保留页面和主流程，但增加或拆分局部模块。

## 八、对现有开发 PRD 的影响

现有《VibeCheck 首期 MVP 开发 PRD》仍可保留通用架构、权限、安全、状态、审核、可访问性和非功能要求，但不能直接作为新品类开发基线。下一版必须更新以下部分：

### 1. 产品与验收基线

- 替换首期品类、用户状态、核心任务、首页频道和验收场景；
- 北极星指标、漏斗和核心埋点改为有效发现、收藏参考、资产/Fork、关系和回流；
- 保留禁止商业推断、低频作者验证和一个 `project_id` 贯穿全局等原则。

### 2. 领域模型与接口

- 将当前 `Project` 拆为 `ProjectCore`＋`CategoryPayload`；
- 定义 `PortfolioSchemaV1` 的校验、版本和迁移接口；
- 更新 `SearchIntent`、`ComparisonSession` 和 `DecisionRecord`；
- 扩充 `ReusableAsset`、`ProjectRelation` 和生命周期子类型；
- 保持通用状态、证据、审核和权限接口兼容。

### 3. 搜索与推荐

- 重建索引字段、同义词、意图解析和初始权重；
- 删除旧 Category 解析字段；
- 增加视觉字典、结构组合、复用条件和可解释匹配原因；
- 规则/编辑策展优先，复杂个性化继续延后。

### 4. 前端页面与表单

- 全量替换模拟作品、截图、字段、标签、筛选和比较行；
- P11 增加可跳过关系模块，A03 分层字段编辑；
- 明确区分“保存比较会话”和“保存创作推进动作”；
- 卡片增强截图和资产入口，但不改变导航和主路由。

### 5. 后台、审核和运营

- A07 管理 Schema 版本与视觉字典；
- A10 支持关系方向、关联资产、证据和确认状态；
- 发布审核增加公开性、个人主体和 AI 辅助证据判断；
- 建立 64 个种子档案的导入、核验和配额看板。

### 6. 测试与数据迁移

- 重写固定模拟数据和 U01—U06 任务，使其覆盖浏览收藏、查同类、比较结构、访问资产、发布、重复分流、关系声明和更新；
- 保留原有登录回跳、比较 2—5 限制、草稿恢复、异常、争议、权限和移动端测试；
- 原型无生产数据，只需代码类型和夹具迁移；生产实现前另行定义在线 Schema 迁移和回滚。

## 九、后续执行顺序

1. 冻结三份新品类正式产品文档和本影响说明；
2. 生成下一版开发 PRD 的领域模型、接口和验收变更；
3. 建立 10 个标准 Portfolio 档案，校准 Schema 和编辑一致性；
4. 更新原型模拟数据、字段、页面文案和比较矩阵；
5. 实现 P11/A03 局部结构修改和 P20 P0.5 能力；
6. 使用新品类任务开展可用性回测；
7. 扩充至 64 个正式种子档案后进入封闭测试。

## 十、最终影响结论

本次切换不需要重做 VibeCheck 的产品骨架。作品社区、统一作品 ID、搜索、详情、比较、发布、作者、生命周期、证据、状态和后台均可继续使用。

真正需要重构的是品类知识层：分类、Category Schema、搜索意图、详情档案、比较维度、资产类型、关系优先级、生命周期子类型、指标和种子数据。通过将 Portfolio 字段从 `ProjectCore` 中分离，本次调整同时修复了未来扩品类时反复重构主对象的风险。
